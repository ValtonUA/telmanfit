# TelmanFit — наскрізна специфікація UX-переробки

> **Статус:** запропонований план робіт, не реалізовано цим Issue.  
> **Дата:** 2026-10-28. **База:** актуальний `master` перед кожним PR.  
> **Обсяг:** шість послідовних, автономних завдань; кожне закінчується **окремим PR із автоматичним SHA-locked merge після незалежного review та всіх обов'язкових gates**.  
> **Мета:** усунути повне перезавантаження сторінок та зробити створення, наповнення й повторення раціонів очевидним для тренера, не послаблюючи бізнес-обмежень.

> **Автономне виконання:** [Issue #107 — UX-AUTO Coordinator](https://github.com/ValtonUA/telmanfit/issues/107). Власник 28.10.2026 прямо погодив **самостійний запуск, перевірку, виправлення і SHA-locked merge UX-1…UX-6 без ручних PR approvals**. Це не стосується production, довільних PR, небезпечних змін БД та нових суттєвих архітектурних рішень. Загальний no-merge default діє поза цим явно дозволеним scope. Координатор має виконувати чинний `scripts/ci/pre_merge.py`, незалежний review та browser acceptance. За блокера зупинитися й надати конкретний звіт.

## Проблема та кореневі причини

**Клієнтський додаток:** React використовується як окремий застосунок, але переходи між вкладками здійснюються через звичайні HTML-посилання (`client/src/components/ClientNavigation.tsx`, `client/src/App.tsx`). Це перезапускає застосунок, знову ініціалізує auth і створює білий спалах: темна тема застосовується лише після появи `.client-main`.

**Filament:** у `app/Providers/Filament/AdminPanelProvider.php` не налаштовано штатну SPA-навігацію. Потрібні перевірка сумісності й тестування власних Livewire/Alpine компонентів, а не переписування адмінки на React.

**Раціони:** `MealPlanFoundation::create` створює порожню версію без днів; редагування заховане в посиланні на ID точної версії; меню «Керування» містить нерелевантні або передчасні дії; drag з каталогу відкриває великий модал через `mountAction('addItem')`; `uom_id` скидається, навіть якщо вибір очевидний; каталог має дві великі колонки; на довгій сторінці зона drop зникає вище екрана; немає окремого копіювання одного дня. Картки тижневого огляду мають недолуге оформлення підписів і градієнта.

**Важливе розмежування:** бізнес-логіка та захист історії в Stage 4 уже реалізовані; змінюємо UX і додаємо потрібні вузькі серверні команди, **не переписуємо ядро заново**.

Не запитувати окреме погодження кожного PR.**

### UX-1 — Справжня SPA-навігація React

**Scope:**
1. Внутрішня навігація всіх чотирьох вкладок («Сьогодні», «Раціон», «Корисне», «Прогрес») і другорядних маршрутів: профіль, безпека, анкета, рецепт за item ID, покупки, помічник приготування, бібліотека, матеріал.
2. Клієнтський router (рекомендовано React Router у декларативному режимі; встановлення нової залежності перевіряти за правилами `AGENTS.md` — потребує належного погодження). Без SSR, Inertia і зміни Laravel API.
3. Header/footer/sidebar/bottom navigation не демонтуються при переходах; URL, Back/Forward, query `week/day`, прямі посилання, refresh і 404 працюють.
4. Прибрати білий спалах: застосувати правильний колір фону/тему до React mount, незалежно від auth-init; локальні loading/error/empty/retry стани не знищують shell.
5. Зберегти ClientSession/CSRF, MFA/OTP/invitation fragment, logout, session-expired, focus/visibility та revoked checks. Немає витоку кешованих даних між користувачами; перевірки доступу виконуються на сервері.
6. Перевірити timers, Wake Lock, асинхронні запити та cleanup під час навігації.

**Acceptance:** на переходах між внутрішніми вкладками немає HTML-document navigation, повторного повного mount/init або білого спалаху; Back/Forward/direct-link, auth і 320/390/1440 px light/dark працюють.

### UX-2 — SPA-навігація Filament 5

**Scope:**
1. Перевірити поточну сумісність Filament 5 + Livewire 4; застосувати штатну `->spa()` / `wire:navigate`, якщо підтверджено.
2. Плавні переходи між ресурсами `/admin` без перезавантаження документа; збереження теми й адекватного стану сайдбару.
3. Перевірити повторний запуск JS після переходів: Filament actions/modals, власний Blade/Alpine/Livewire код, каталог, редактор раціонів і рецептів, DnD, сповіщення.
4. Захистити auth/MFA, logout, CSRF, server validation, session expiry. Несумісні маршрути дозволено виключати **точково**, із поясненням і тестами.

**Acceptance:** переходи без document reload, без подвійних event listeners або broken modals; Back/Forward; без регресій у діях та доступах; 320/390/1440 px light/dark.

### UX-3 — Створення раціону та зрозуміла навігація

**Scope:**
1. При створенні нового раціону **в одній серверній транзакції** створювати логічний план, рівно одну draft-версію, 7 днів і стандартні прийоми їжі (запропоновано: сніданок, обід, вечеря, перекус), з можливістю змінити вибір до створення. Позиції залишаються порожніми.
2. Типи брати **лише з реальних `meal_types`** за перевіреними code/ID; не створювати фіктивних type IDs чи seed. Для відсутнього довідника — інформативний стан і безпечна відмова.
3. Правильний `week_start_weekday`; створення атомарне/ідемпотентне щодо дубльованого запиту; GET/reload не пише в БД.
4. Новий раціон одразу відкриває тижневий редактор; в списку та деталях — очевидне посилання **«Редагувати раціон»** і клікабельна назва чернетки. Для published показувати чіткий read-only статус, не приховані ID.
5. Існуючі порожні drafts не мігрувати мовчки: явна одноразова дія «Створити 7 днів». Ніяких змін published/assignments/history.
6. Узгоджено змінити стару документаційну вимогу про порожню чернетку в `docs/meal-plans.md`; відповідні тести оновити як частину зміни контракту.

**Acceptance:** створив раціон → одразу 7 днів з вибраними прийомами → можна редагувати одним кліком; транзакційність, concurrent/retry guards, жодної мутації історії.

### UX-4 — Компактний редактор дня та зручна навігація

**Scope:**
1. Дві десктопні робочі області: прийоми їжі зліва, каталог справа. Їхні прокручування незалежні в доступній висоті вікна, drop target завжди можна досягти. Коректні scroll/focus при зміні пошуку і на тач-пристроях.
2. Каталог: **три компактні картки в ряд на широкому екрані**, адаптація 2/1 при нестачі місця; невеликі фото сталого aspect ratio, назва, тип, зрозуміла дія додавання і drag handle.
3. Прийоми виглядають як очевидні drop zones; зрозумілі empty states. На мобільних — доступна кнопка/вибір прийому без обов'язкового drag.
4. Меню «Керування» прибрати з редактора дня як переповнений список; винести публікацію, повторення і керування тижнем до тижневого огляду; cover рецепта — до редактора рецепта. Дії з позицією розміщувати на її картці.
5. Підписи: «Додати прийом їжі», «Додати продукт або страву», «Змінити кількість» — замість безконтекстних технічних назв.

**Acceptance:** два доступні одночасно робочі стовпці при довгому каталозі; три картки на широкому desktop; 320/390/1440 без overflow; клавіатура/touch, light/dark. Цей PR **не переписує writer і не реалізує UX-5**.

### UX-5 — Швидке додавання і редагування позицій

**Scope:**
1. Drop каталожного продукту в конкретний прийом не відкриває великий Filament modal. Якщо параметри однозначні — через штатний writer одразу створити позицію, зберігаючи серверну перевірку.
2. Якщо параметри неоднозначні — компактний **inline editor** в місці додавання; поки не підтверджено, записів немає. Можна скасувати.
3. Одна допустима одиниця вимірювання — автоматичний вибір, без зайвого select. Кілька — лише перевірений default/явний вибір. Не вигадувати кількість грамів чи порцій.
4. Legacy/Model I/A/B/C: точна published recipe version, format/divisor/selector; жодних silent latest і автоматичного необґрунтованого A/B/C вибору.
5. Порядок позицій автоматично визначається місцем drop; приховати `sort_order` від звичайного користувача. Зміна кількості доступна прямо з картки.
6. Touch/keyboard fallback, drop/reorder, duplicate submit, stale state, unauthorized, rollback, CAS/signed-token/concurrency guards.

**Acceptance:** продукт з однозначними параметрами додається однією дією; неоднозначний — через inline підтвердження; немає великого модала для звичайного drop; жодних часткових записів, втрати порцій або зміни published history.

### UX-6 — Копіювання дня та фінальний огляд тижня

**Scope:**
1. «Копіювати день» на огляді й у редакторі. Джерело — конкретний день поточної точної draft-версії, ціль — один/кілька/решта шість днів тієї самої версії.
2. Копія включає структуру прийомів, type/title/order, items, exact food/recipe references, quantity/UOM, batch format/divisor, frozen selectors, усі чинні важливі поля. **Незалежні нові child IDs**, source не змінюється.
3. Порожні цілі заповнити без зайвих підтверджень. Для непорожніх — preview точних днів, прийомів і позицій + явне підтвердження перед заміною; cancel не записує нічого. Не допускати silent overwrite.
4. Доменна команда з lock ordering, stale/CAS/HMAC/replay/rollback, аналогічно чинному `MealPlanWeekRepeater`; authorisation draft-only.
5. Огляд тижня: 7 колонок, однакові пропорції фотографій, охайний внутрішній padding, м'який нижній градієнт, контрастні підписи й кількості; чіткі дії «Редагувати», «Копіювати», «Повторити тиждень», «Опублікувати».
6. Зберегти існуючі правила публікації, повторення тижнів, призначень та frozen history.

**Acceptance:** заповнив понеділок → скопіював у шість днів → 7 правильних незалежних днів; stale/cancel не перезаписують цілі; published незмінний; 320/390/1440 px light/dark; публікація без регресії.

## Наскрізні нефункціональні вимоги та DoD для кожного PR

- **Вхід:** перед змінами обов'язково читати `AGENTS.md`, `docs/roadmap.md`, `docs/project-status.md` та предметні файли; перевірити свіжий `master`, конфлікти з уже відкритими PR та Feasibility Gate.
- **Дані:** жодного самовільного production/Telmanfit_dev доступу, міграцій або очищення даних; для тестів — лише ізольована disposable PG18 зі synthetic fixtures. No silent autofix/backfill legacy.
- **Безпека:** без послаблення Policy, CSRF/MFA/session/ACL, CAS/lock/deferred constraints, version exactness та immutable published/assigned.
- **Перевірки:** релевантні Unit/Feature/PG18 negative+concurrency для серверних змін; browser Chromium desktop 1440, mobile 390/320, light/dark; переходи, keyboard/touch, помилки API, refresh, stale і неавторизований доступ.
- **Докази:** короткий human walkthrough основного сценарію, скриншоти/перелік перевірок, SHA останнього head, статус GitHub CI, відомі ризики й обмеження; не називати неуспішний CI успішним.
- **Документація:** оновити відповідні канонічні контракти (`docs/client-app.md`, `docs/meal-plans.md`, roadmap/status за потреби) в тому ж PR; не маскувати зміни контракту лише правками коду.
- **Вихід:** один PR на завдання до `master`. Після незалежного review, browser evidence, чинних Fast/Docs/Targeted на точному SHA і `pre_merge.py eligible:true` — **автоматичний SHA-locked merge**, без ручного погодження кожного PR; GitHub auto-merge без gate заборонено. Після merge оновити чекбокс, PR URL та merged SHA. Якщо gate не пройдено — виправити й перевірити повторно або зупинитися з конкретним блокером.

## Контрольний користувацький сценарій після завершення всіх етапів

1. Клієнт: «Раціон» → «Корисне» → «Прогрес» → «Сьогодні» без перезавантаження HTML або білого спалаху, зі збереженням теми та стану авторизації.
2. Адмін: переходить між довідниками, рецептами та раціонами без повного reload.
3. Тренер: «Створити раціон» → 7 днів з прийомами → заповнити понеділок перетягуванням продуктів із компактного каталогу → швидко змінити кількість → скопіювати день на решту тижня → переглянути 7 днів → опублікувати.
4. Для будь-якої помилки, невалідного доступу або конкурентної зміни немає втрати чи тихої підміни даних.

## Відкриті рішення, які не можна приймати мовчки

- React Router у декларативному режимі для UX-1 **погоджений у межах цього плану**. Інші нові сторонні сервіси, платні інтеграції чи зміни архітектурних меж потребують окремого рішення.
- Стандартні типи прийомів їжі — прив'язати до реальних `meal_types` у цільовій БД, не припускати числові ID або наявність seed.
- Для неоднозначних кількостей і фізичних форматів рецепта немає silent defaults; вибір користувача обов'язковий.
- Увімкнення Filament SPA дозволено лише після доведеного збереження поведінки існуючих сторінок та auth/MFA.
