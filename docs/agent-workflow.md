# Робочий цикл ChatGPT → Codex для TelmanFit

Канонічний цикл **feature/* → master**, незалежний review, Windows-приймання та дозвіл merge після приймання визначено в [feature-environments.md](feature-environments.md). Постійна `dev` не використовується.

Мета — отримувати **перевірений результат**, а не довгі плани, звіти чи PR без виконаної функції. Це рекомендації щодо процесу; дозволи й заборони визначає [AGENTS.md](../AGENTS.md), а правила CI — [ci.md](ci.md).

## Ролі й 7 практик

1. **Коротке завдання.** Указуй результат, спосіб перевірки, межі й лише важливі обмеження. Не диктуй агенту алгоритм там, де його визначають наявний код і тести.
2. **Незалежна перевірка.** Після реалізації — self-review diff, релевантні unit/integration/PG/browser тести та негативний сценарій. Для UI перевіряй видимий шлях користувача, а не лише успіх API; тест має виявляти регресію. Self-review не дорівнює незалежному review і не гарантує кратного приросту якості.
3. **Критерії готовності замість «продовжуй».** Для багатокрокового результату сформулюй завершальний стан і докази. Якщо встановлений Codex підтримує `/goal`, можна використати його; це стан **конкретного thread**, не безмежний фоновий процес і не дозвіл на merge. Для короткої задачі звичайний prompt.
4. **Мало постійних правил.** `AGENTS.md` — спільні, відносно короткі інваріанти; `CLAUDE.md` — тільки посилання; деталі — в предметних docs. Не копіювати історію PR і технічні специфікації у системні інструкції.
5. **Нові правила — за доказом.** Якщо агент повторив помилку, спершу зафіксуй мінімальне відтворення та тест. Потім обери один рівень виправлення: код/тест, детермінований guard, предметна документація або правило агента. Не накопичуй дублікати заборон.
6. **Обмеження виконувати кодом, де можливо.** Справжні гарантії для production забезпечують права доступу, окремі середовища, серверні правила і CI/pre-merge. Додатковий локальний `PreToolUse` hook блокує лише очевидні руйнівні Bash-команди; він не контролює всі інструменти або обхідні способи запуску.
7. **Рекомендації на рівень вище.** Спочатку доведи основний результат. Далі коротко вкажи 1–2 покращення UX, безпеки або підтримуваності, якщо є перевірені підстави. Самостійно виконуй необхідні супутні виправлення в межах мети; окремі продуктові рішення та заборонені дії потребують дозволу.

## Як перевіряти впровадження

| Практика | Механізм і доказ | Межа |
|---|---|---|
| 1. Коротке завдання | Шаблон нижче і контекст за потребою в AGENTS | Якість конкретного завдання залежить від доступного контексту |
| 2. Незалежна перевірка | Тести, self-review та предметний review за складністю | Self-review не є незалежним рев’ю; автоматично залучити іншого агента не завжди можливо |
| 3. Критерії готовності | Приймальні докази та перевірка CI на фінальному head | `/goal` залежить від можливостей і налаштувань клієнта |
| 4. Мало постійних правил | Один канонічний AGENTS, посилання з CLAUDE і предметні джерела | Завантаження інструкцій залежить від клієнта |
| 5. Нові правила за доказом | Спочатку відтворення і regression test | Рішення про нове правило потребує оцінки людини або агента |
| 6. Виконувані обмеження | Sandbox, права, CI та опційний hook із regression tests | Hook не є межею безпеки і потребує довіри |
| 7. Рекомендації | Self-review і короткі пропозиції, засновані на фактах | Корисність пропозицій залежить від задачі; не генеруй їх примусово |

Це перевірюваний робочий контракт, а не твердження, що кожен клієнт автоматично забезпечує всі сім практик. Для кожного PR доказами є відповідний diff, релевантні тести та перевірки на актуальному SHA.

## Мінімальний контракт задачі

```text
Результат: <що повинно працювати після зміни>.
Приймання: <конкретний сценарій у продукті + автоматизовані перевірки>.
Межі: <що не змінювати; production/реальні БД/merge — лише за чинним дозволом>.
Працюй автономно: перевір код, внеси зміни, сам переглянь diff, запусти
релевантні тести, виправ помилки. Створи Draft PR за дозволеним scope.
Не називай задачу завершеною без доказу. Якщо основний результат
дійсно заблоковано — назви точну передумову та найменшу дію для розблокування.
```

**Приклад для UX редактора раціону** (шаблон, **не дозвіл поновити** призупинені UX-4–UX-6):

```text
Результат: тренер створює раціон, бачить 7 днів і може відразу редагувати
перший прийом їжі без пошуку технічної версії.
Приймання: Chromium 1440/390/320 light/dark, сценарій створення →
редагування → повторне відкриття; PG негативні тести історії та ACL.
Межі: без нових бізнес-правил, production, реальної БД або merge.
```

## Порядок виконання та підтвердження

1. Перевір актуальний head, зміни інших агентів і пов'язані Issue/PR. Для зміни файлів працюй у власній гілці.
2. Перевір мінімальні критичні передумови **саме цієї задачі**. За часткової відсутності локального тестового середовища розрізняй: дефект функції, дефект тестового harness і відсутність production-доступу. Не створюй фальшивих PASS.
3. Зроби найменший наскрізний результат, потім self-review й перевірки: поведінка, негативний тест, регресії, diff. Якщо тест падає — встанови причину та виправ; не повторюй безкінечно той самий запуск.
4. Для PR наведи exact head SHA, список тестів із результатами, Docs-Impact, відомі обмеження. Fast/Docs/Targeted і `scripts/ci/pre_merge.py` — перед merge на конкретному SHA. Злиття дозволене після продуктового приймання exact head/base власником і фінального gate, без додаткового погодження технічної операції.
5. Підсумок: **готово / частково / заблоковано**; що фактично змінилося, як перевірено, що не перевірено і найкоротший наступний крок. Не плутай синтетичний тест, локальний PASS, CI PASS і робочий production.

## Локальні Codex hooks

У репозиторії: `.codex/hooks.json` та `.codex/hooks/pre_tool_policy.py`. Підключення проєктних hooks вимагає довіри до `.codex/` і **окремого підтвердження незміненої конфігурації** у Codex CLI через `/hooks`. У неперевіреному середовищі не вважай hook активним.

Перевірка правил: `python3 -m unittest discover -s tests/ci -p 'test_agent_hook.py' -v` (на Windows: `py -3 -m unittest discover -s tests/ci -p test_agent_hook.py -v`). Вони також входять у наявний CI-набір `tests/ci`.

Hook за замовчуванням відмовляє `git push --force` (також явний `+` refspec), `git reset --hard`, `git clean --force`, `php artisan db:wipe`, `migrate:fresh`, `migrate:refresh` у Bash. Для Artisan він враховує глобальні опції перед командою, зокрема `--env=testing` і `--env testing`, а також шляхи до `artisan`. Це додатковий захист від випадкових команд, **не** повна перевірка довільного shell-синтаксису, підстановок, скриптів, інтерактивного вводу `write_stdin`, PowerShell-команд або MCP/API. Якщо hook не довірений, не запускається, завершується помилкою або викликається іншим шляхом, захист може не спрацювати. Жоден hook не надає нових дозволів і не скасовує обмеження [AGENTS.md §4](../AGENTS.md#4-заборонено-без-прямого-дозволу-користувача).

Наявна пауза UX-4–UX-6 з [Issue #106](https://github.com/ValtonUA/telmanfit/issues/106) і [#107](https://github.com/ValtonUA/telmanfit/issues/107) лишається чинною до окремого рішення власника.
