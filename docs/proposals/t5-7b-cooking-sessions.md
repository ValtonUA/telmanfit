# T5.7b — кухонні сесії та мегарецепти: контракт для погодження

> **Статус:** клієнтський UX і гібридні токени (§3.1–3.3) погоджено власником 27.10.2026; предметна SQL-модель, політика публікації та порцій/зберігання ще **не затверджені**. Лише документаційна пропозиція у Draft PR, без SQL/міграцій/Filament/API/React/production-змін. Джерела чинних правил: [client-app.md](../client-app.md) §4, [meal-plans.md](../meal-plans.md), [recipe-batches.md](../recipe-batches.md), DBML, BR-P/BR-F/BR-X.

## 1. Предметні межі та багаторазовий шаблон

Кухонна сесія — **організація приготування кількох страв в одному процесі**, не A/B/C-формат однієї страви у `recipe_batch_*`.

**Виправлення попередньої пропозиції:** кухонний *шаблон* не прив'язується до одного `assignment_id` та номера календарного тижня. Тренер створює шаблон **для конкретного складу опублікованого меню (exact frozen recipe selectors, portions, days/layout) і конкретного режиму готування**. Такий шаблон потенційно застосовується повторно в кількох тижнях і для кількох клієнтів, **лише якщо сервер довів точну сумісність структури меню та порцій**.

Порівнювати за назвою («1500 ккал», «Меню A»), тільки ID meal plan чи тільки загальною калорійністю — **недостатньо**. Кандидат: versioned immutable `menu_pattern` / source fingerprint, що однозначно охоплює frozen `meal_items`, recipe versions, format/divisor, кількість споживаних порцій та відносні дні циклу. Конкретний fingerprint, межі циклу та версіонування мають бути визначені *до* SQL. Жодної silent «latest version» підміни.

**Календар і права доступу** — окреме застосування шаблону: конкретний client `assignment_id` + server week/date, актуальна published версія, доступні дні. При зміні призначення або його періоду доступу клієнт не бачить непідтверджених сесій; повторення циклу меню не можна автоматично вигадувати (DEC-5M не затверджено). Частковий тиждень потребує підтвердженої сумісності або unavailable; жодних phantom днів. Клієнт не може відкрити чужу історію/чернетки.

Режими: «щодня / двічі на тиждень / раз на тиждень» — **бажаний формат**, не гарантія безпечної зберігаємості. Тренер може опублікувати лише ті режими, які вручну підготував. Якщо для цього складу меню й режиму немає сумісного шаблону, показуємо чесне «План приготування не підготовлено».

## 2. Погоджений клієнтський UX

### 2.1. Перша сторінка перед початком

Перехід із вкладки «Раціон» веде на **сторінку-заголовок кухонної сесії**, не на перший крок. Порядок блоків:

1. Необов'язковий короткий вступ автора, потім **«Що приготуємо»**: страви, точні порції для цього застосування та вручну заданий орієнтовний час.
2. Одразу **перемикач «Не вимикати екран»** із фактичним станом (активно/не підтримується/втрачено).
3. Помітна кнопка **«Почати!»**, або «Продовжити» за наявності чинного локального прогресу.
4. **«Що знадобиться»**: компактна адаптивна решітка обладнання (орієнтовно 3–4 елементи в ряд, назва над зображенням); далі список інгредієнтів — маленьке зображення зліва, праворуч назва й точна кількість, наприклад «Гречка — 350 г». Безпечні зображення за чинними правилами; за відсутності фото назва й кількість залишаються читабельними.
5. **«План приготування»**: усі логічні етапи, номер + назва, без повного тексту дій.

Режим «Увесь план» — **ця вступна сторінка**, а не ще один повноцінний дубль редактора.

### 2.2. Режим «Готую зараз»

**Один екран — один логічний етап, межі визначає автор.** Етап може мати 2, 5 або більше дій; немає продуктового ліміту на кількість дій. Відображення:
- прогрес-бар етапів і номер поточного етапу;
- назва етапу;
- чіткий **нумерований список дій** із точними кількостями, жодних checkboxes/обов'язкових відміток;
- **ситуативні** елементи: зображення, підказка з назвою **«Підказка»**, один чи декілька таймерів. Якщо автор їх не додав — елементи не займають місця;
- звичайно **одне основне зображення**. Автор може додати ще, але UI не показує всі зображення одночасно великим потоком: доступ до решти за явною дією користувача;
- **закріплена нижня панель** з великими кнопками «Назад» / «Наступний етап» (padding з урахуванням safe area на мобільних);
- поточні/завершені таймери в компактній панелі, що **не зникає після переходу до іншого етапу**.

Користувач **сам** перемикає етап. Завершення таймера не здійснює auto-next і **не означає готовність їжі**. «Контрольний етап» не додається як окрема сутність у MVP: автор може звичайним етапом написати «Перевірте готовність» або «Підготуйте фасування».

### 2.3. Локальний прогрес і відновлення

Після reload/випадкового закриття клієнт продовжує **з останнього відкритого етапу**. Запущені таймери відновлюються за збереженим абсолютним часом завершення, а не за кількістю `setInterval` ticks. Перехід етапів, вкладок, згортання застосунку та пауза в UI **не зупиняють** реальні таймери.

Пропозиція MVP: тільки мінімальний локальний стан (ідентифікатор чинної версії/сесії, індекс етапу, timer ID, `ends_at`, стан, wake-lock preference), без тексту рецептів, токенів, персональних/медичних даних. Ключ прогресу жорстко прив'язаний до **авторизованого клієнта + конкретного застосування шаблону/дати + версії**; при logout/revocation/зміні assignment/сесії очищення й повторна перевірка права доступу **перед** показом. Для повторного використання одного шаблону іншим клієнтом **ніколи** не переносити його прогрес. Доступ між різними пристроями в MVP не обіцяємо. Остаточний client-storage/TTL/auth-boundary перевірити при реалізації.

### 2.4. Таймери MVP

- Кожен таймер є **окремим структурованим авторським блоком** із timer ID, назвою («Гречка»), тривалістю в секундах та повідомленням після завершення («Перевірте готовність гречки»). Запуск — **тільки за кнопкою** у відповідному етапі (не автоматично з відкриттям).
- Підтримуємо кілька **незалежних** паралельних таймерів, відлік не зникає під час переходів між етапами; UI показує завершення, дає зупинити/перезапустити.
- Звуковий сигнал у **видимому відкритому застосунку**, якщо браузер дозволяє відтворення аудіо після взаємодії користувача. На поверненні з фону показати фактичний прострочений статус і попередження.
- **Не обіцяти надійний сигнал при заблокованому телефоні чи закритому браузері.** Фонові таймери можуть обмежуватися ОС/браузером. Web Push/системний фон — **пізніше**, окреме рішення.
- Тривалість є орієнтиром виконання конкретної авторської дії, не автоматичною гарантією готовності чи безпеки продукту.

### 2.5. «Не вимикати екран» — обов'язковий елемент UX

Перемикач на вступній сторінці; активує `navigator.wakeLock.request('screen')` під час видимого кухонного режиму, якщо HTTPS/браузер/OS/заряд дозволяють. **Потрібно показувати реальний стан**, не лише бажане значення. При втраті wake lock (`visibilitychange`, battery saver, page hidden) пробувати безпечно перевідкрити його після повернення у видимий режим, якщо опція лишається ввімкненою; не приховувати відмову. На завершенні приготування й вимкненні перемикача звільняти ресурс. Без fallback-хаків, що тримають телефон увімкненим всупереч системі.

### 2.6. Фасування та зберігання

Завершальні етапи створюються автором як **звичайні кроки** з можливими фото/підказками/таймерами. Клієнт бачить конкретні контейнери, порції, дати/умови охолодження, зберігання, розморожування й розігрівання **тільки якщо це вручну перевірено автором**. Не генерувати «безпечні дні зберігання» за загальним припущенням. Реальне змішане готування й точні порції вимагають окремих server publish guards.

## 3. Редактор Filament 5 — погоджений задум інтерфейсу

В admin **список шаблонів → редактор шаблону → редактор кухонної сесії**, з обов'язковим **клієнтським preview** перед publish. Для редактора кроків використати **наявні штатні компоненти Filament 5** (без окремого стороннього JS редактора як першого кроку):
- **Repeater етапів**: автор додає/клонує/перейменовує/видаляє draft етапи, згортає їх і перетягує у довільний порядок. **Назва етапу** — обов'язкове поле, не довільний блок.
- **Builder усередині етапу**: drag-and-drop упорядкованих ситуативних типів `action`, `image`, `hint`, `timer`. Можна повторювати типи і комбінувати довільно: 2 чи 10 action, жодної підказки, кілька таймерів. Кількість фото не обмежувати продуктово, але в client UI одночасно велике тільки одне.
- **Action** — текст одного нумерованого кроку, гібридні токени кількостей за §3.1 та ручні параметри автора; без довільних формул, фінансових чи нутриційних розрахунків.
- **Image** — перевірений HTTPS URL/керований R2 asset за існуючими правилами, alt; жодного raw HTML або довільних хостів.
- **Hint** — необов'язковий короткий текст, на клієнті заголовок «Підказка».
- **Timer** — label, ціла тривалість у секундах, необов'язковий текст після завершення; валідація розумних меж перед збереженням/publish.
- Стабільні **block IDs** незалежно від drag reorder, аби локальний стан таймерів і версії не переплутувалися. Порядок етапів і блоків — авторський, версіонований.

Наявний **Builder** Filament підтримує різнотипні блоки та drag-and-drop; **Repeater** підтримує перевпорядкування. Спочатку перевірити UX, доступність, nested schemas і персистентність у Chromium/Livewire на актуальній версії; якщо вкладений Builder створює проблеми, дозволено замінити його на **один Builder етапів із вкладеним Repeater дій/медіа**, без переписування всього адмін-інтерфейсу.

Ніяких чекбоксів виконання для клієнта, на відміну від форм редагування для тренера.

### 3.1. Погоджене продуктове рішення: гібридні токени

**Автоматично — лише кількості інгредієнтів із точних frozen версій рецептів та сума явно вибраних автором рядків.** Вода для приготування, обладнання (кількість, місткість, тип), температура, час, тривалості таймерів та інші технологічні параметри задаються й підтверджуються автором вручну. Навіть якщо вода є рядком рецепта, її технологічну кількість у кухонній інструкції не виводити автоматично. Не обчислювати воду з крупи, літри каструлі з маси або час із кількості порцій. Жодних довільних формул, виразів, скриптів, вкладених обчислень чи автоматичного масштабування часу/обладнання.

Чинний [RecipeTokens](../../app/Services/Recipes/RecipeTokens.php) лишається основою для **одного рецепта**: `{{ingredient:<row_id>:quantity}}` / `:grams`, а також наявні equipment tokens; remap рядків, plain text і відмова для невідомого/пошкодженого токена перевірені [RecipeTokensTest](../../tests/Unit/RecipeTokensTest.php). Він отримує вже вибраний формат і не виконує багаторецептні суми. Його чинні equipment tokens та A/B/C-політики **не переносяться як автоматичне обладнання в T5.7b**; зміни Stage 3 або DEC-3T тут не погоджуються.

Для T5.7b потрібен окремий resolver кількох точних frozen рецептів і вручну заданих параметрів сесії, без перевантаження чинного синтаксису. Кандидатна семантика, **не затверджений API/JSON/SQL**:

| Значення | Джерело та межа |
| --- | --- |
| Окрема кількість | Явне посилання на конкретний CookingOutput, exact recipe version, фізичний формат і стабільний ingredient row ID; frozen quantity/UOM або grams. Назва продукту не є ключем. |
| Авторська сума | Іменована автором група з явним списком посилань на рядки конкретних outputs, одним показником (quantity або grams) та цільовою одиницею. Немає автоматичного включення інших однойменних продуктів. |
| Ручний параметр | Явне авторське значення/текст у версії шаблону або структурованому блоці таймера; не формула й не автоматична підстановка equipment із рецептів. |

Брати **фізичну кількість приготування**, а не множити її на `assigned_servings`: B/7 — весь frozen B; C/3 і C/4 мають той самий фізичний C, але різний divisor. Legacy — точні збережені кількості й servings_count. Два прийоми їжі з одного CookingOutput не подвоюють склад. Повторне фізичне приготування представляється окремим явним output, не прихованим множником токена. Довільного масштабування інгредієнтів за новими порціями також немає.

Сума дозволена лише для того самого ingredient identity та сумісного frozen контексту. Для quantity потрібні однакові одиниця й frozen семантика conversion; несумісні UOM/factors відхиляються, без live conversion. Для grams — лише frozen grams рядків того самого продукту. Використовувати точну decimal арифметику без float і закупівельного округлення, відхиляти overflow, пропуски, дублікати того самого output+row та неоднозначні посилання. Не підсумовувати різні продукти за однаковою назвою й не зливати frozen revisions мовчки.

Синтетичний приклад: автор вибрав 200 г гречки з output X і 150 г тієї самої гречки з output Y — токен суми показує 350 г із доступним автору переліком джерел. Третій рядок гречки не додається сам. Текст «Додайте 700 мл води в каструлю 2 л; готуйте 20 хв при 180 °C» і timer=1200 секунд — ручні авторські значення, а не результат цієї суми.

### 3.2. Сумісність перед повторним використанням — fail closed

Перед publish, у клієнтському preview та **при кожному застосуванні/читанні** сервер перевіряє в узгодженому read snapshot:

1. Поточні права ClientSession, exact assignment, server week/date, доступні дні та режим; exact published версію шаблону й меню без підміни на latest.
2. Весь склад меню: exact frozen recipe versions, ingredient row IDs та ingredient identities, quantity/grams/UOM і доступні frozen conversion snapshots; формат, divisor, виготовлені й призначені порції, зв'язки outputs/allocations, залишки та відносні дні. Не лише рядки, згадані в тексті. Різні portions/divisor або нова версія рецепта — несумісність, навіть при однаковій назві/ккал чи фізичній масі.
3. Кожне посилання й групу суми, відсутність дублікатів/пропусків/неоднозначності та актуальність ручного авторського підтвердження для **цього складу і порцій**. Зміна залежностей у draft скидає review; потрібні новий preview і явне підтвердження параметрів автором. Published не змінюється.

Mismatch, відсутні frozen дані, неповний тиждень без підтвердженої відповідності чи unresolved token блокують **усю інструкцію**; не показувати частково правильні дії, старий preview, нулі, raw токени чи fallback на live каталог. Повідомити unavailable/conflict за контрактом доступу, очистити нечинний локальний прогрес. Автор створює нову версію й перевіряє її вручну; сервер не «пристосовує» рецепт, воду, час або обладнання до нового клієнта.

### 3.3. Критерії майбутньої реалізації (тут тести не додавалися)

- Позитивні: окрема frozen quantity/grams, авторська сума лише вибраних рядків із provenance, повторне сумісне застосування двом клієнтам з ізольованим прогресом; фізичний batch не дублюється через allocations.
- Негативні: інша recipe version/ingredient identity/row, кількість/UOM/factor, portions/divisor (зокрема C/3 → C/4), режим/дні/partial week, відсутній snapshot, dangling/unknown/malformed token, чужий output, дубль у сумі, overflow, довільна формула та спроба автоматичного water/equipment/time token.
- Зміна draft складу скидає ручне підтвердження; fail closed до нового review. Preview і client read дають однакові значення; revoked/replaced assignment не відновлює стару інструкцію після reload. Усе plain text із штатним escaping, без виконання виразів.
- Сервісні/Unit перевірки resolver, негативні PG перевірки майбутніх persisted guards та Chromium intro/player — в окремій реалізації. Поточні тести RecipeTokens не доводять реалізації гібридних токенів.

## 4. Кандидатна модель (НЕ затверджені назви таблиць)

| Сутність | Відповідальність |
| --- | --- |
| **CookingTemplate** | Ідентичність **складу опублікованого меню/циклу** + режим 7/2/1, автор, draft/published, version/immutable snapshot, явна заміна попередньої версії |
| **CookingSessionTemplate** | Відносний день/порядок сесії, тривалість, обладнання та вступ; **послідовність етапів і блоків** як валідований versioned JSONB із стабільними IDs |
| **CookingOutput** | Фізичний batch конкретної опублікованої версії рецепта та правильного A/B/C або legacy формату; виготовлені порції/залишки |
| **CookingAllocationPattern** | Відносна позиція прийому їжі у складі меню, кількість споживаних порцій, FK/selector до CookingOutput; без hard FK лише на client-specific `meal_items.id` за замовчуванням |
| **Runtime session state** | **Не частина authoring content.** Мінімальний клієнтський progress/timers, ізольований за user+assignment/date+template version; спосіб зберігання й TTL — окремий технічний висновок |

Одного великого JSONB для всіх зв'язків недостатньо: coverage/portion/recipe selectors повинні мати надійні PostgreSQL guards; натомість редакторський список етапів/блоків може бути versioned JSONB із server validation і UI schema.

## 5. Обмеження й кандидати інваріантів публікації

1. Лише admin/Filament може створювати/змінювати draft; published **immutable**; нова редакція через окремий draft. Сесії, етапи, блоки й allocations версіонуються разом.
2. Перед publish сервер доводить, що всі `CookingOutput`/`CookingAllocationPattern` узгоджені з exact frozen recipe versions/formats/portion divisor; жодного округлення, подвійного споживання чи «latest».
3. Перевірити повноту приготування/винятки для ready-to-eat, часткові тижні та **точну сумісність reusable template** за §3.2 при кожному client read; усі токени й авторські суми мають пройти §3.1, інакше вся інструкція unavailable. Заявлена повторюваність клієнтського меню не підміняє DEC-5M.
4. Валідувати типи блоків, порядок, стабільні IDs, дозволені URL і тривалість таймерів, відсутність HTML/XSS, достатність storage та порціонування до publish.
5. Клієнтський API — поточна ClientSession, exact assignment scope, 401/404/409 fail-closed, `Cache-Control: no-store, private`, GET/HEAD без DML; при зміні доступу очищувати вміст і локальний runtime progress.

## 6. Неузгоджені архітектурні рішення перед SQL

- **D1.** Як канонічно зіставити *повторюваний склад меню* між тижнями/клієнтами без помилок DEC-5M: reusable `menu_pattern` identity/fingerprint, partial-week policy та exact selectors?
- **D2.** Підтвердити immutable published template/versioning, одне джерело prepared output для конкретного meal item у v1, звірку приготовано/призначено/залишилося.
- **D3.** Які typed дані зберігання/порціонування мають бути обов'язковими для publish, а які залишаються текстом автора; хто підтверджує безпеку?
- **D4.** Автор може публікувати лише наявні безпечні режими 7/2/1, а клієнт бачить empty/unavailable — кандидат на затвердження.
- **D5.** Рекомендований MVP: **один сумісний шаблон**, одна повна сесія з кількома стравами, валідовані action/image/hint/timer блоки, React intro + cooking player, локальний resume/wake lock, synthetic PG/Chromium; із погодженими гібридними токенами §3.1–3.3, без автогенерації, сесійних покупок, Web Push, кроспристроєвого progress і production.

**Не реалізовано:** нових таблиць/міграцій, API, Filament-конструктора, клієнтського cooking player, фактичних push/таймерів або production-змін. Гібридні токени вже погоджені як продуктове рішення; це не погодження SQL-моделі, D1–D5 чи імплементації. Після погодження D1–D5: окремий migration/schema PR, потім Filament/ClientSession/React + isolated tests; кожен PR — Draft до окремого merge approval.
