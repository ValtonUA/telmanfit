# T5.7b — кухонні сесії та мегарецепти (пропозиція, НЕ затверджено)

**Статус:** тільки предметний review. Жодних SQL/міграцій, API, Filament або React-реалізацій цим документом не дозволено. Затверджені рамки: [клієнтський UX `4](../client-app.md), Model I, [рецепти A/B/C](../recipe-batches.md), BR-P/BR-F/BR-X, [календар](../meal-plans.md).

## 1. Мета та перевірені передумови

**FEASIBILITY: PASS для проєктування.** У коді/схемі вже є точні призначення (`client_meal_plan_assignments.id`), опубліковані версії (`meal_plan_version_id`), прийоми/`meal_items` та селектори форматів A/B/C. Календар T5.2 визначає дні/тижні на сервері; T5.3 надає незмінні харчові потреби. **FEASIBILITY імплементації ще не підтверджена до погодження кандидатів нижче.**

Клієнт обирає один із уже погоджених режимів: **щодня (орієнтир 7), двічі на тиждень (2), раз на тиждень (1)**. Тренер вручну готує, перевіряє й публікує інструкції. Режим **не гарантує** такої частоти для довільної страви та не змінює продуктовий список. Якщо конкретний режим не підготовлений, показуємо його недоступність, а не генеруємо рецепт.

**Кухонна сесія готує кілька страв.** Це не існуюча фізична партія *одного* рецепта у таблицях `recipe_batch_*`. Перейменовувати/перепризначати їх не можна.

## 2. Прив'язка та історія

Кожен план готування прив'язаний до **одного exact assignment ID**, його immutable `meal_plan_version_id`, номера тижня за DEC-5C та режиму. Початковий частковий тиждень береться з фактично доступних дат, не з 7 днів від `start_date`. Друга клієнтська картка навіть із тією самою published-версією плану не отримує чужий kitchen plan.

При заміні/завершенні призначення або зміні доступного інтервалу старий план не повертається як чинний. Історичний запис зберігається, але **не віддається клієнту за fallback**. Нове опубліковане редагування має створювати нову версію; старі published записи не переписуються.

## 3. Кандидати сутностей (НЕ назви для міграцій)

| Сутність | Мінімальна відповідальність |
| --- | --- |
| **CookingPlan** | `assignment_id`, server `week_number`, режим, статус draft/published, автор, ревізія, явна заміна попередньої редакції |
| **CookingSession** | дата приготування, назва, короткий вступ, приблизна тривалість, обладнання, ручні нумеровані фото-кроки, охолодження/зберігання/розігрів |
| **CookingOutput** | одна приготовлена фізична партія exact published рецепта, обраний формат A/B/C або legacy, кількість цілих партій, вихід порцій та залишок |
| **CookingAllocation** | зв'язок конкретного `meal_items.id` призначеного тижня з приготовленим CookingOutput, кількість споживаних порцій |

**Чому не один JSON:** сервер повинен перевірити FK, own-client scope, exact published version, двійне включення позиції та покриття порцій. Кроки/фото сесії можуть бути одним обмеженим JSONB *усередині* CookingSession, щоб не вводити окремі таблиці для кожного кроку; виходи/allocations залишаються реляційними. Остаточні ключі, UNIQUE/CHECK, NUMERIC і CAS потребують окремого SQL-review.

## 4. Пропоновані інваріанти публікації

1. Лише admin/Filament створює, змінює draft і публікує після ручного preview. Опублікований CookingPlan, sessions, outputs, allocations — **immutable**; нова редакція через окремий draft, без delete/backfill історії.
2. Кожен allocated `meal_items.id` належить exact published версії призначення, а його дата — тільки фактично доступному тижню. Заборонені інші клієнти, чужий тиждень, неопублікована версія та підміна формату.
3. **Спожиті порції ≠ фізично приготовлені партії.** Тренер явно вказує виготовлені порції, розподіл між прийомами й залишки; сервер перевіряє покриття без від'ємних кількостей, подвійних allocation і непомітного округлення. Рецепти, які не потребують готування, вимагають явного винятку з причиною; фрукт/інгредієнт без рецепта не створює фіктивну кухонну сесію.
4. Batch-вихід прив'язаний до точної опублікованої версії й формату: A/1, B/7, C/3 або 4; legacy має `servings_count`. При несумісності партій/порцій публікація відхиляється, а не домислює фізичний вихід.
5. Зберігання — **ручна, перевірена інструкція** для конкретних страв: охолодження, холодильник/заморозка, контейнери, розморожування, розігрів і дати споживання. Ніякого припущення «7 днів безпечно в холодильнику»; відсутність придатної інструкції блокує publish.
6. ClientSession API read-only, `no-store, private`, 401/404/409 fail-closed, GET/HEAD без DML. При зміні assignment/revocation — очистити UI. Клієнт не обчислює порції й не бачить чужих/старих/чернеткових матеріалів.

## 5. Запропонований UX

«Раціон» → «Приготування та покупки» → тиждень → **щодня / 2 рази / 1 раз**. Показувати тільки явно опубліковані тренером кухонні сесії; відсутня версія режиму — порожній стан. Сесія містить список кількох рецептів із порціями, обладнання, фото-кроки, розподіл у контейнери та правила зберігання. Покупки за тиждень лишаються T5.3/T5.7a; покупки за конкретною сесією, упаковки/SKU та автоматичні мегарецепти — **поза MVP**.

## 6. Відкриті рішення власника

- **D1.** Чи погоджуємо immutable published cooking plans і окремий draft на заміну, збереження історії без актуального fallback? **Рекомендую так.**
- **D2.** Чи допускаємо *одне* джерело CookingOutput для кожного `meal_item` у v1 (без розщеплення одного прийому між двома сесіями)? **Рекомендую так.**
- **D3.** Чи погоджуємо окремий облік **виготовлено / призначено / залишилося** та обов'язкове ручне підтвердження storage-інструкцій для кожної сесії? **Рекомендую так.**
- **D4.** Чи тренер може публікувати **лише доступні** режими, а клієнт бачить чесне «план не підготовлено»? **Рекомендую так** замість обов'язкового ручного написання 7+2+1 сесій.
- **D5.** Чи погоджуємо **мінімальне доказове впровадження**: один авторський режим, синтетичний тиждень, декілька рецептів, одне published підтвердження і строгі SQL/API guards — потім масштабування? **Рекомендую так.**

Після погодження D1–D5: окремий PR з авторитетними SQL → DBML → Entity Catalog/BR, forward-only міграціями та PG негативними тестами; наступні PR Filament editor, read-only ClientSession API і React. Без production-змін без go/no-go.

**Свідомо НЕ виконано:** нових таблиць/полів, міграцій, додаткових залежностей, бізнес-операцій, API, UI, реальних даних чи production-змін.
