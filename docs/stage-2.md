# Stage 2 — картки клієнтів

> **UX-1:** українська локалізація панелі, компактні мобільні картки, семантичні статуси та локальний аватар — [реалізація, браузерні докази й межі](ux-1.md). Нижче збережено звіт початкового Stage 2; твердження про відсутність браузерної перевірки стосується PR #6.

Реалізація в `feat/stage2-client-cards`, Draft PR #6, на основі `master`, що містить merge PR #5 (`3c74349e5525100b9c9fbb5809a27c94e1231ad6`). Обсяг G5 — перший бізнес-модуль «Картки клієнтів»; весь Stage 2 roadmap, зокрема клієнтська API-авторизація, цим не закривається.

## Погоджене рішення G1

21.10.2026 користувач прямо обрав: **«Користувача з role=coach або role=admin»** для `clients.coach_user_id`. Адміністратор обирає тренера явно; немає default, автоматичного створення користувача, призначення поточного admin чи зміни ролей. Відсутність придатного користувача означає неможливість зберегти картку до його окремого створення/призначення ролі. Цей модуль не керує користувачами чи ролями.

`coach` може бути відповідальним тренером, але не має доступу до Filament. `ClientPolicy` дозволяє список, перегляд і редагування тільки `admin`; створення заборонене всім ролям; видалення не передбачене. BR-U-08 забороняє однакові `user_id` і `coach_user_id` (самосупровід).

## Поведінка

- `/admin/clients`: ID картки, акаунт/ім’я/email за наявності, відповідальний тренер, статус, дата початку; пошук за ID, ім’ям/email акаунта та ім’ям тренера, фільтр за статусом.
- Нові клієнти отримують доступ виключно за персональним запрошенням тренера. Ручне створення адміністратором заборонене: CreateAction прибрано; `ClientPolicy::create()` повертає false для всіх ролей; `CreateClient::authorizeAccess()` безумовно повертає 403 при mount, hydrate і create. Старий `/admin/clients/create` залишено заблокованим, включно з прямим Livewire-доступом і викликом create зі старої форми.
- Наявні `user_id=NULL` зберігаються як перехідні записи; кілька таких записів не порушують UNIQUE. Їх можна переглядати й редагувати. `user_id NOT NULL` не запроваджується.
- У поточній погодженій схемі `clients` **немає імені, телефону чи email**. До прив’язки акаунта картка відображається як «Без акаунта» й визначається ID. Ім’я авторизованого користувача зберігатиметься в `users.name`; `clients.display_name` не додається, анкета чи профілі не використовуються як обхід.
- Необов’язкова прив’язка наявного акаунта: пошук за ім’ям/email, підпис із ID. Один акаунт має щонайбільше одну картку; її можна редагувати, прив’язати або відв’язати акаунт. Нові акаунти цей ресурс не створює. Це явне редагування перехідного запису, а не реалізація підтвердженої Telegram-прив’язки; пошук не встановлює автоматично тотожність людей.
- `pending`, `active`, `paused`, `finished`. `coaching_started_at` встановлюється автоматично, коли `active` вперше зберігається без дати, при редагуванні наявної картки. Пауза, завершення й повторна активація зберігають дату; форма не дозволяє її вручну переписувати. Інших обмежень переходів погоджена схема не визначає. Час показується в UTC.
- У моделі `Client` перевіряються FK, роль тренера, самосупровід, UNIQUE акаунта та статуси; форма також перевіряє введення. PostgreSQL зберігає свої CHECK/NOT NULL/UNIQUE/FK як остаточний захист. Масові SQL/Query Builder-оновлення не запускають Eloquent events; їх не слід використовувати для бізнес-запису в обхід моделі.
- `Client::user()` і `Client::coach()`, `User::client()` і `User::coachedClients()`. Додаткові профільні моделі й рядки не створюються.

## Затверджена ціль і відкриті рішення

Одна людина має один обліковий запис `users` і максимум один профіль `clients`. PWA, Telegram Mini App або обидві оболонки використовують спільні дані через Laravel API і PostgreSQL та максимально один React-застосунок. Mini App може мати обмежений набір можливостей.

У PWA передбачено «Підключити Telegram» з підтвердженням володіння Telegram-акаунтом; зворотний сценарій також має підтримувати підключення до того самого акаунта. Автоматичне ототожнення людей за ім’ям, username чи email заборонене. Реєстрація не активує платний супровід.

Механізм запрошень, Telegram-автентифікація, прив’язка Telegram та PWA-автентифікація **ще не реалізовані**. До їх реалізації створення нових клієнтів через UI недоступне. Спосіб браузерної автентифікації PWA, деталі токенів запрошень і повний процес онбордингу **ще не погоджено**; PR #6 їх не визначає. Відкриті питання — [roadmap.md](roadmap.md), T2.4/T2.5, та [schema-audit.md](schema-audit.md), розділ «Відкриті рішення реєстрації».

## Перевірки

Відтворення: `npm run lint --prefix client`, `npm run build --prefix client`, `PAO_DISABLE=1 tests/pg/run-stage1.sh`. Раннер запускає міграції лише на **новій** тимчасовій PostgreSQL 18.6 у контейнері без мережі/портів, SQL-регресію, обидва PHPUnit-набори та Pint, потім прибирає власний контейнер/socket. Спільний `PostgresTestCase` зберігає guard: жодного fallback на наявну БД. GitHub Actions використовує той самий раннер.

Оновлені тести перевіряють відмову ручного створення через HTTP, Policy, прямий Livewire і create для admin/coach/client; відсутність кнопки та підроблений виклик дії зі списку; редагування перехідних NULL-карток у всіх статусах; явний coach/admin; відсутність автоматичної активації від акаунта/профілю. Збережено пошук/фільтр/перегляд, першу активацію/паузу/повторну активацію, унікальність акаунта, самосупровід, валідацію підроблених ID, DB-обмеження, доступ ролей і гостя. Усі фікстури синтетичні; прямі створення моделі в тестах готують наявні записи й не відкривають UI-реєстрацію.

Фактичний повний прогін коригування в Linux Codex Cloud: `PAO_DISABLE=1 tests/pg/run-stage1.sh` → код 0; PostgreSQL 18.6, SQL **PASS=76 FAIL=0 GAP=0**, PostgreSQL PHPUnit **37 tests / 645 assertions**, основний PHPUnit **19 passed / 26 assertions**, Pint успішний; **warnings і skipped немає**. `npm run lint --prefix client`, `npm run build --prefix client` і `bash tests/pg/test-runner.sh` → код 0. Власний контейнер/socket прибрано раннером. Результат GitHub Actions на останньому коміті буде зазначено в описі PR #6 після завершення CI.

## Межі перевірки

HTTP-відповіді й Livewire-компоненти перевіряються автоматично; візуальна браузерна перевірка не виконувалася. Для ручної перевірки на вже налаштованому середовищі: у списку немає кнопки створення, прямий `/admin/clients/create` повертає 403 для admin/coach/client, а гість переходить на `/admin/login`. На наявних картках перевірити пошук, фільтр, редагування тренера/статусів і UTC.

Наявні локальні БД, production, секрети, еталонні SQL/DBML, міграції та залежності не змінюються. Анкетування, механізм запрошень та клієнтська автентифікація не реалізуються в цьому коригуванні; цільовий хостинг та решта G1 залишаються відкритими. PR залишається Draft; нового PR і Merge немає.
