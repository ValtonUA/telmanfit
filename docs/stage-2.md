# Stage 2 — картки клієнтів

Реалізація на `master`, що містить merge PR #5 (`3c74349e5525100b9c9fbb5809a27c94e1231ad6`). Обсяг G5 — перший бізнес-модуль «Картки клієнтів»; весь Stage 2 roadmap, зокрема клієнтська API-авторизація, цим не закривається.

## Погоджене рішення G1

21.10.2026 користувач прямо обрав: **«Користувача з role=coach або role=admin»** для `clients.coach_user_id`. Адміністратор обирає тренера явно; немає default, автоматичного створення користувача, призначення поточного admin чи зміни ролей. Відсутність придатного користувача означає неможливість зберегти картку до його окремого створення/призначення ролі. Цей модуль не керує користувачами чи ролями.

`coach` може бути відповідальним тренером, але не має доступу до Filament. `ClientPolicy` дозволяє список, перегляд, створення й редагування тільки `admin`; видалення не передбачене. BR-U-08 забороняє однакові `user_id` і `coach_user_id` (самосупровід).

## Поведінка

- `/admin/clients`: ID картки, акаунт/ім’я/email за наявності, відповідальний тренер, статус, дата початку; пошук за ID, ім’ям/email акаунта та ім’ям тренера, фільтр за статусом.
- Створення без реєстрації: `user_id = NULL`, типово `pending`, тренера треба обрати. Кілька карток без акаунта дозволені.
- У поточній погодженій схемі `clients` **немає імені, телефону чи email**. До прив’язки акаунта картка відображається як «Без акаунта» й визначається ID. Для збереження імені незареєстрованої людини потрібне окреме бізнес-рішення та погодження зміни схеми; анкета чи профілі не використовуються як обхід.
- Необов’язкова прив’язка наявного акаунта: пошук за ім’ям/email, підпис із ID. Один акаунт має щонайбільше одну картку; її можна редагувати, прив’язати або відв’язати акаунт. Нові акаунти цей ресурс не створює.
- `pending`, `active`, `paused`, `finished`. `coaching_started_at` встановлюється автоматично, коли `active` вперше зберігається без дати, зокрема при створенні активної картки. Пауза, завершення й повторна активація зберігають дату; форма не дозволяє її вручну переписувати. Інших обмежень переходів погоджена схема не визначає. Час показується в UTC.
- У моделі `Client` перевіряються FK, роль тренера, самосупровід, UNIQUE акаунта та статуси; форма також перевіряє введення. PostgreSQL зберігає свої CHECK/NOT NULL/UNIQUE/FK як остаточний захист. Масові SQL/Query Builder-оновлення не запускають Eloquent events; їх не слід використовувати для бізнес-запису в обхід моделі.
- `Client::user()` і `Client::coach()`, `User::client()` і `User::coachedClients()`. Додаткові профільні моделі й рядки не створюються.

## Перевірки

Відтворення: `tests/pg/run-stage1.sh`. Раннер Stage 1 автоматично включає нові тести `tests/Postgres/ClientResourceTest.php`, запускає міграції на **новій** тимчасовій PostgreSQL 18.6 без мережі/портів, SQL-регресію, обидва PHPUnit-набори та Pint і прибирає власний контейнер/socket. Спільний `PostgresTestCase` зберігає guard із Stage 1: жодного fallback на наявну БД. GitHub Actions використовує той самий раннер.

Тести охоплюють чотири статуси при створенні, редагування/прив’язку акаунта й тренера, першу активацію/паузу/повторну активацію, пошук/фільтрацію/перегляд, підроблені ID, відсутнього або непридатного тренера, невалідний статус, дубль акаунта, самосупровід, DB-обмеження в обхід Eloquent, гостя й admin/coach/client через HTTP, Policy та Livewire. Фікстури синтетичні.

Фактичний прогін у Linux Codex Cloud: `PAO_DISABLE=1 tests/pg/run-stage1.sh` → код 0; PostgreSQL 18.6, SQL **PASS=76 FAIL=0 GAP=0**, PostgreSQL PHPUnit **33 tests / 660 assertions** (21 новий тест клієнтського модуля + 12 тестів Stage 1), основний `php artisan test` **19 passed / 26 assertions**, Pint успішний; warnings і skipped немає. Перевірено реальні HTTP-відповіді й Livewire-компоненти; ручна браузерна перевірка залишається нижче. Cleanup власного контейнера й socket завершився успішно.

## Локальна перевірка інтерфейсу

На середовищі з уже застосованими міграціями Stage 1 й існуючим admin відкрити `/admin/clients`. Перевірити пошук/вибір тренера, створення без акаунта, пошук за ID, прив’язку наявного акаунта, перегляд, редагування та статуси/фільтр. Переконатися у зручності «Без акаунта» з ID і відображенні UTC. Під coach/client усі чотири URL повинні повертати 403; гість переходить на `/admin/login`.

У Cloud наявні локальні бази не використовувались. Production, секрети, еталонні SQL/DBML, міграції та залежності не змінено. Анкетування, Telegram, харчування, клієнтський API й додаткові функції поза обсягом; перевірка цільового хостингу й решта G1 залишаються відкритими. PR має залишитися Draft без Merge.
