Функціональні межі й архітектура — [architecture.md](docs/architecture.md), бізнес-інваріанти — [business-rules.md](docs/business-rules.md).

## 2.2. Межа Windows / WSL для локального TelmanFit

- **Код, тести, PR:** Codex у WSL2 Ubuntu; isolated/disposable Docker і синтетичні дані — лише за §4.
- **Штатне оновлення існуючого `telmanfit-local`:** Windows PowerShell 5.1 у фактичному **Windows checkout** Compose-проєкту (на поточному ПК — `C:\\Projects\\telmanfit` лише після звірки label `com.docker.compose.project.working_dir`). Єдина штатна команда з кореня каталогу — `.\\scripts\\local-update.ps1`. У ній уже є Git fast-forward, Compose identity, RestoreFence, allowlist, backup/restore rehearsal, health gate. Не дублюй ці перевірки окремим багатокроковим Codex-preflight без конкретного інциденту; не запускай coordinator з Linux checkout.
- **Особливість Windows/WSL:** помилка виклику `powershell.exe` із WSL (`UtilBindVsockAnyPort`, interop) **не означає**, що Windows PowerShell, GitHub або Docker Desktop не працюють. Перейди до нативної Windows PowerShell-команди; не вимагай лагодження WSL interop як умову локального оновлення. Не роби висновків про Windows DNS із DNS у WSL.
- **Git-дерево:** точний untracked файл `?? compose.r2-runtime.yaml` — дозволений виняток у `Assert-SafeGitTree`; його не можна видаляти, комітити чи переписувати заради «чистого» дерева. Інші зміни оцінює штатний coordinator.
- **Помилка coordinator:** не повторювати команду навмання, не виконувати ручні міграції або cleanup volumes; спершу прочитати фазу і журнал у `%LOCALAPPDATA%\\TelmanFit\\updates`. При незавершеній міграції/backup погодити окремий recovery-план. Деталі — `docs/local-compose.md`.
- **Комунікація:** якщо користувач хоче «оновити/запустити локально» після merge, одразу давай одну штатну Windows PowerShell-команду й коротку інструкцію, як передати помилку; не створюй новий PR, аудит чи серію завдань Codex без фактичної потреби.

## 2.1. Обов'язковий Feasibility Gate (перевірка здійсненності)

**Спершу доведи, що головний результат досяжний; лише потім витрачай ресурси на реалізацію.** Це правило діє для нетривіальних завдань, особливо якщо результат залежить від зовнішнього API, облікових даних, реальних записів БД, експорту, стороннього сервісу чи недоступного середовища. Просте документаційне редагування без таких залежностей не потребує окремої тривалої перевірки.

1. **Визнач головну мету та критерій приймання.** Назви обов'язкові джерела даних, потрібні поля й ідентифікатори, середовище, інструменти, доступи та дозволи. Відокрем основний результат від допоміжних робіт (команда, тести, документація, PR).
2. **Перевір критичні передумови фактично й мінімальними read-only діями.** Наявність схеми БД не доводить наявності записів; визначені змінні середовища — працездатність API; тести на синтетичних даних — можливість отримати результат на реальних даних. Не роби висновків про фактичні ID/відповідності без перевіреного джерела цих даних.
3. **Не обходь безпеку задля preflight.** Обмеження §4 щодо production, реальних БД, секретів та персональних даних залишаються чинними. Якщо для результату потрібні дані з реальної БД, а дозволеного доступу немає, зупинись і запроси найменший безпечний read-only експорт конкретних полів або окреме погодження доступу. Не підключайся до production самовільно.
4. **Зафіксуй короткий висновок до змін:** `FEASIBILITY: PASS` — усі критичні передумови перевірено; `FEASIBILITY: PARTIAL` — критична перевірка не завершена; `FEASIBILITY: BLOCKED` — хоча б одна критична передумова відсутня. Назви підтвердження або блокер і мінімальну наступну дію. Некритичні обмеження можна описати окремо, не позначаючи їх як блокування.
5. **Fail closed:** для `PARTIAL` або `BLOCKED` **негайно завершуй завдання** з коротким звітом. Заборонено переходити до коду, міграцій, рефакторингу, тестових «замінників» основного результату, комітів, PR, повного CI або тривалих збірок без нового явного погодження зміненого scope. Інструкції «працюй автономно», «не зупиняйся через дрібниці» та загальний дозвіл на PR не скасовують цю вимогу.
6. **Витрати мають слідувати за доказом.** Після `PASS` реалізовуй насамперед найменший вертикальний сценарій, що доводить головний результат; лише потім — розширення, документацію та відповідні тести/CI. Автоматичні GitHub checks можуть запускатися за правилами репозиторію; не ініціюй зайвих ручних Full CI/повторів без підстав.
7. **Два етапи для зовнішніх залежностей.** Якщо мета прямо вимагає реальних сторонніх даних або доступу до зовнішнього сервісу, за замовчуванням спочатку виконай **окреме preflight-завдання без змін репозиторію** і заверши його висновком. Реалізацію починай наступним завданням після підтвердженого `PASS` та доручення користувача. Якщо користувач прямо замовив лише ізольований прототип/тестовий код, познач обмеження і не заявляй, що перевірив реальні дані.

**Критерій:** успішні тести, створена команда або Draft PR не компенсують невиконаний головний результат. Правило діє разом із Definition of Done (§14) і не розширює жодних дозволів на зміну реальних систем.

## 4. Заборонено без прямого дозволу користувача

**Обсяг дозволу:** явно погоджене завдання на реалізацію/PR дозволяє потрібні **звичайні** зміни коду, тестів, документації, створення гілки, `git add/commit/push` у власній гілці та Draft PR. Не вимагай окремого дозволу на кожну безпечну команду. Це **не** дозвіл на merge, схему поза scope, робочі дані чи destructive Git.

- Не вигадуй нові таблиці, поля, enum, довідникові значення, бізнес-правила, залежності або зміну архітектури. Погоджені зміни схеми документуй синхронно в SQL/DBML/Entity Catalog/BR і тестах; нові залежності — лише за погодженням.
- **Завжди заборонено без окремого дозволу:** merge/auto-merge, force-push, rebase/reset/clean зі втратою змін, видалення чужих файлів, історичних даних чи каталогів, очищення `storage/`.
- **Реальні середовища:** не запускати `migrate*`, `db:wipe`, `db:seed`, ручні `UPDATE/DELETE/TRUNCATE/DROP/ALTER` і масові backfill без окремо погодженого плану, preflight, backup/rollback. Не брати production/Telmanfit_dev, секрети, Telegram-токени або персональні дані для тестів.
- **Тестова БД:** дозволені погоджені в scope міграції, SQL й негативні перевірки **лише у новій ізольованій disposable PostgreSQL 18** із синтетичними даними, без зовнішніх портів, із cleanup. Не переносити це право на реальні БД.
- Не вмикай feature flags або production auth/Telegram/бізнес-модулі без окремого go/no-go.
- Не встановлюй Laravel Boost: `laravel/boost` навмисно не використовується.

## 5. Технологічний стек і жорсткі межі

- Laravel 13, PHP (точні підтримувані patch constraints — `composer.json`), PostgreSQL 18, PHPUnit 12, Pint; Filament 5 — панель `/admin`.
- React 19 + TypeScript + Vite у `client/`: збірка до `public/app`, сторінки під `/app/{any?}`.
- Browser API під `/api` повертає JSON: public health stateless, auth/protected підгрупи — штатні Laravel session/CSRF. **Не називати весь /api stateless.** SPA звертається лише до цього API.
- Inertia.js не використовувати; Blade є в Laravel/Filament, а не клієнтським SPA. Зберігати наявну структуру шарів і залежностей.

## 6. Запроєктоване vs реалізоване

- **Запроєктовано** — погоджений контракт без повної реалізації; **реалізовано** — підтверджений код, міграція й тести; **активовано** — окремо підтверджений runtime/production go/no-go.
- Перед роботою звіряй `app/`, `database/migrations/`, `routes/`, `client/src/` та предметні тести. Не вважай успішний SQL baseline доказом готових сервісів/UI.
- Не доповнюй схему «на льоту» заради зручності реалізації. Відсутність даних T1.5 не дає права вигадувати фасування, SKU чи seeds.

## 7. Незалежність бізнес-логіки від Telegram

- Публікація рецептів/планів, розрахунки, призначення, прогрес і повідомлення — доменні сервіси Laravel. Telegram — окремий канал/адаптер, без `chat_id`/`initData` в домені.
- Telegram authentication/ownership, retry, idempotency й захист персональних даних належать інтеграційному шару; веб-кабінет не залежить від Telegram.
- PWA та Mini App використовують один користувацький акаунт/API, Mini App може мати менший набір функцій; не ототожнювати акаунти за ім'ям, username або email.

### Затверджена реєстрація клієнтів

- Нові клієнти — тільки за персональним запрошенням від `admin`; створення карток в обхід invitation через UI/HTTP/Livewire/Policy заборонено.
- Одна особа — один `users` і максимум один `clients`; `users.first_name/last_name`, обчислюване `full_name`, лише погоджений legacy fallback; `clients.display_name` не додавати.
- Реєстрація не активує платний супровід. Відповідальний `coach/admin` обирається явно, Filament — лише для `admin`.
- Історичні `clients.user_id=NULL` дозволено зберігати й редагувати; не додавати `NOT NULL` і не створювати нові неавторизовані картки.
- Деталі OTP/MFA, Telegram linking та поточна activation-межа — [auth-architecture.md](docs/auth-architecture.md), [client-profiles.md](docs/client-profiles.md), roadmap і код.

## 8. Робота зі схемою БД

- Захищай погоджені PG18 CHECK/FK, `btree_gist`, `EXCLUDE` на перекриття призначень, partial UNIQUE, DEFERRABLE guards, publication immutability та editor-contract/lineage. Не прибирай DB-захист заради проходження тесту.
- `text + CHECK` у PostgreSQL та логічні enum у DBML — погоджена відмінність.
- Стандартну Laravel-міграцію `users` не переписуй; зміни додавай forward-only міграціями у визначеному scope. Діючі legacy/published дані зберігати без вигаданого backfill.
- `phpunit.xml` використовує SQLite in-memory; поведінку PG18 перевіряй окремими ізольованими наборами.
- Підтверджені SQL-контракти та правила переходу мають вищий пріоритет за здогадки агента.

## 9. Тести

- Кожне реалізоване правило повинно мати автоматизований тест; DB-правила — також сервісну перевірку та **негативний PG-тест**.
- У негативних тестах **дозволено навмисно невалідні синтетичні записи** для доказу відмови та rollback; заборона вигадувати невалідні production дані до них не стосується.
- PHPUnit 12: `tests/Unit` — чисті розрахунки, `tests/Feature` — HTTP/інтеграція, `tests/Postgres`/`tests/Auth*` — специфічні PG/Auth інваріанти. Не додавати Pest без дозволу.
- Backend: `php artisan test` / `composer test`; PG/schema: disposable PostgreSQL18, відповідні runners; SPA: `npm run lint --prefix client` та `npm run build --prefix client`. Візуальні зміни — browser/light/dark/responsive за scope.
- Якщо перевірку не запущено, напиши причину; не видавай локальний PASS за GitHub CI на фінальному head.

## 10. Стиль і конвенції

- PHP: PSR-12, Laravel Pint, типізовані сигнатури; не додавай `declare(strict_types=1)` без узгодженості з сусідніми файлами.
- Laravel: `app/Models`, `app/Http/Controllers/Api`, `app/Filament`, `routes/api.php`; не перейменовуй SQL-поля заради Eloquent.
- API — JSON, `snake_case` та Laravel validation; жодного HTML із `/api`.
- React hooks/function components; явно типізуй TypeScript там, де це необхідно (`client/tsconfig.app.json`); дотримуйся ESLint і наявного Tailwind.
- Документація, повідомлення й коментарі українською; ідентифікатори англійською.

## 12. Git та службові команди

- Перед змінами — `git status/diff/log` і актуальний `master`; працюй у власній гілці. `git add/commit/push` для погодженого PR дозволені без мікропогодження.
- Не перезаписуй чужі зміни; безпечне оновлення гілки без force-push. Merge, rebase/reset із ризиком втрат, видалення і зміни production — лише після відповідного дозволу.
- Конфлікти або неможливість безпечної синхронізації — повідом як blocker, не обходь захист.
- Локальні dev/build/test-команди допустимі в межах завдання; реальні БД та секрети залишаються забороненими за §4.

## 13. Звіт після задачі (обов'язковий)

Українською: (1) зроблено; (2) усі змінені файли; (3) виконані тести й результати; (4) ризики та неперевірене; (5) відкриті предметні рішення; (6) свідомо не виконане; (7) PR, head SHA, CI/Docs-Impact за наявності.
Не називай Draft PR або локальну збірку merged/production-ready.

## 14. Definition of Done

Реалізація в погодженому scope, інваріанти захищені кодом і БД, тести/форматування пройдено, чинна поведінка документована, незавершене явно позначено, звіт за §13 надано.
Створення Draft PR **не** дозволяє merge; якщо CI incomplete — робота може бути готовою до review, але не до merge.

## 16. Політика актуальності документації (обов'язково для кожного PR)

**Одне твердження — одне канонічне місце.** Не дублюй поточні PR, SHA, Stage, відсоток готовності, feature flags і датовані PASS в AGENTS, README або architecture. Застарілий текст **замінюй**, не додавай спростування зверху.

| Зміна в PR | Канонічне оновлення |
|---|---|
| Функціональний прогрес або пріоритет | `docs/roadmap.md`; факти/докази — `docs/project-status.md` |
| Реальна поведінка UI/API/auth, тести | `docs/project-status.md` і відповідний предметний контракт |
| Архітектура, runtime, hosting | `docs/architecture.md` |
| Бізнес-правила / БД | Предметні SQL, DBML, Entity Catalog, BR, forward-міграції — лише в погодженому scope |
| Нові/перейменовані файли, посилання | Оновити прямі посилання й навігацію |
| Тільки тести, документація або рефакторинг без зміни контракту | Обґрунтований `Docs-Impact: none — ...` або зміна конкретного канонічного тексту |

`Documentation health` та `scripts/docs_guard.py` перевіряють посилання, roadmap і PR-base docs-impact; це **не гарантія семантичної правильності тексту**. Не обходити guard косметичними змінами.

**Merge-gate для агента:** лише після **окремого дозволу на merge** і предметного review виконати `python3 scripts/ci/pre_merge.py <PR> --repo ValtonUA/telmanfit` із довіреного checkout. Потрібні Fast PR checks, Docs links/roadmap/PR impact і Targeted PR checks — `completed/success` на **актуальному head SHA**, master є предком head, немає auto-merge. Failed/cancelled/pending/skipped/старі SHA чи attempts блокують merge. Full CI не запускається й не є вимогою для жодного diff, label чи критичного шляху. Після зміни head або base повторити три required checks і gate. Безпосередньо перед merge повторити gate й використовувати `--match-head-commit <SHA>`. Деталі — [ci.md](docs/ci.md).

Серверний GitHub branch protection може бути недоступний: тоді це обов'язковий **агентський** захист, який технічно може обійти людина/admin. Не дозволяй auto-merge та не видавай `eligible: true` за право злити PR без рішення власника.
